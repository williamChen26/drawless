# Drew 产品定位

## 一句话定位

Drew 是 Drawless 中进入同一块协作画布、可以自然沟通并共同完成工作的数字同事。用户可以和他聊天、讨论想法、交代工作、补充信息、反馈结果、审核计划并接收交付，而不是操作一个需要管理 session 的 AI Chat。

## 命名体系

- `Drawless` 是产品与协作画布空间的名称。
- `Drew` 是这位数字同事面向用户的稳定姓名，用于在场入口、对话、状态、计划、审批和交付。
- `画布搭档` 是首次介绍 Drew 时使用的角色说明，不替代他的姓名。
- `coworker` 是代码、目录、共享类型、控制接口和部署配置中的内部领域名称，不进入普通用户文案。
- 用户可见语言统一使用“找 Drew”“写给 Drew”“Drew 正在处理”，不混用 Coworker、AI 助手、Agent 或画布助手。

## 核心判断

Drew 首先是一位持续存在的同事，其次才是能力入口。Drew 不需要模拟人类外形；他的活体光标本体是诞生于无限画布中的稳定身份。

- 真实同事不会要求用户新建、切换或删除一段 session；Drew 也不向用户暴露这类模型。
- 真实同事既能正常聊天，也能接受工作、提出问题、提交计划、等待审核、执行并交付；Drew 不应被收窄为任务执行器。
- 用户与 Drew 的关系是连续的。页面刷新、一次工作完成或关闭交流界面，都不代表这段关系被重置。
- 对话是协作的基础，不是需要避免的形态；需要避免的是“消息气泡 + session 列表 + 新建会话”主导的通用 AI Chat 产品结构。

## 产品心智模型

### Drew 是同事

Drew 具有稳定身份、在场状态、连续记忆和明确能力边界。在场入口代表“去找这位同事”，而不是“打开一个 AI 功能”。

用户可以自然地：

- 闲聊或交换想法；
- 询问画布内容和工作建议；
- 交代一项希望完成的工作；
- 在执行前补充背景或修改要求；
- 审核 Drew 提交的工作计划；
- 对阶段结果提出反馈；
- 验收交付，或要求继续调整。

### Room 是共同场所

Room 是用户、其他协作者和 Drew 共享的工作场所与上下文，不是聊天 session，也不等同于一次原子任务。

一个 room 内可以自然发生多轮讨论、多次工作推进和多次交付。它们共享当前画布、协作者关系和房间语境，但不需要被用户拆分成多段会话。

如果产品存在多个 room，它们代表不同的协作场所、项目或工作空间，而不是为了清空上下文而创建的“新对话”。

### 对话连接工作，结构化物件呈现责任

普通沟通和正式工作对象应当共存：

| 协作行为 | 推荐呈现 | 是否改变工作状态 |
| --- | --- | --- |
| 闲聊、提问、交换意见 | 轻量对白或信息片 | 通常不改变 |
| 交代工作、补充要求 | 用户消息或交接信息片 | 可能进入理解或计划阶段 |
| 澄清与反馈 | 双向对话 | 更新共同理解 |
| 提交工作计划 | 结构化计划卡 | 进入等待审核 |
| 审核与授权 | 明确的审批动作 | 允许、拒绝或要求调整 |
| 执行进度 | 状态与里程碑 | 更新执行状态 |
| 完成工作 | 交付卡与画布成果 | 进入验收或后续调整 |

对话负责建立共识；计划、审批和交付浮层负责把关键事实呈现清楚。不能把所有交流都强制升级成任务，也不能把审批降级为一句含糊的聊天文本。

这里的气泡、信息片和文档玻璃都是界面呈现，不是统一的业务实体。底层需要区分：

- Tool call：coworker runtime 正在申请调用某项能力的执行事实；
- Approval request：某次高影响能力调用需要用户授权的安全事实；
- Delivery：一次执行完成后可供用户理解和验收的结果事实；
- Work item：只有未来确实出现跨多轮、可分派、可追踪的长期工作时才单独建模。

因此不建立笼统的 `WorkCard` 领域模型，也不要求所有能力套进同一种任务结构。界面可以把不同事实投影成统一风格的工作物件，但不能反向让视觉容器限制 AI tool、审批协议和后续能力扩展。

## 核心体验闭环

1. 用户点击 Drew 的活体光标本体，找到 Drew。
2. 用户可以直接聊天、提问，也可以交代希望完成的工作。
3. Drew 根据意图自然回应；信息不足时先沟通，不急于执行。
4. 涉及受控操作时，Drew 提交可审核的计划卡片。
5. 用户明确允许、暂缓或提出调整；模糊表达不自动视为授权。
6. Drew 执行工作，并通过真实状态和里程碑反馈进度。
7. Drew 推送交付卡片，画布继续承载真实成果。
8. 用户可以验收、反馈或继续讨论，交流自然延续，不创建新的 session。

## 交互原则

### 一个入口，一位同事

- 活体光标入口始终代表 Drew 本人。
- 点击 Drew 本体的稳定含义是“打开与 Drew 的协作空间”。
- 不把本体同时设计成历史切换器、结果开关或 session 管理入口。
- Hover、形态与动作只表达 Drew 的真实状态，不暗中改变工作内容。

### 对话可以轻，工作必须清楚

- 普通聊天使用低负担、易阅读的交流形态。
- 计划、审批、风险和交付使用与事实类型匹配的结构化工作物件。
- 长篇结果先给摘要，再按需展开；画布修改以成果定位和完成回执为主。
- 结构化工作物件可以出现在交流脉络中，但不能退化成普通消息气泡。

### 持续关系，不暴露 session

用户界面不提供：

- 新建会话；
- session 列表；
- 清空上下文后重新开始；
- 第 N 轮对话；
- 将一次回复包装成一个独立 AI 任务。

底层为了传输、鉴权、模型记忆或并发控制，可以存在 `sessionId`、`thread`、`run`、`turn` 等技术概念，但它们不能成为产品信息架构，也不能泄漏为用户需要理解的操作。

### 连续记忆应符合人的预期

Drew 的记忆应按三个边界组织：

- 关系记忆：稳定偏好、长期合作方式和双方约定；
- Room 记忆：当前工作场所中的画布语境、决定、反馈和交付；
- 临时执行状态：一次计划、审批或工具运行的技术现场。

这些边界用于保证相关性、权限和可恢复性，不用于让用户管理“会话”。

## 安全与授权原则

- 普通聊天不能隐式获得画布写权限。
- “可以”“就这样”“你看着办”等含糊表达不能自动批准高影响操作。
- 正式执行必须通过明确、可审计的审批动作。
- 用户提出调整后，旧计划应失效，并由 Drew 提交新计划。
- 画布始终是画布成果的唯一事实源；交流记录不复制第二份画布状态。

## 明确不做

- 不做带 session 侧栏和“新建对话”的通用 AI Chat。
- 不把 Drew 做成只接收命令的任务机器人。
- 不把每条用户消息都解释成需要执行的工作。
- 不用逐 token 打字感代替真实的理解、计划、执行和交付状态。
- 不为了拟人化而伪造进度、情绪或系统没有发生的行为。

## 产品语言

推荐使用：

- 找 Drew；
- 和 Drew 说点什么；
- 交代工作；
- 补充说明；
- 调整一下；
- 工作计划；
- 等你确认；
- 正在处理；
- 交付给你；
- 协作往来。

避免使用：

- 新建会话；
- 新任务（作为清空上下文的入口）；
- session；
- 第 N 轮对话；
- assistant message；
- 重新生成回复。

## 成功标准

当体验成立时，用户应自然地说：

> “我去问一下 Drew。”

> “我把这件事交给他，他给了我一个计划。”

> “我调整了要求，他改完以后把结果交付给我了。”

而不是：

> “我新建了一个会话，给 Agent 发了一个 Prompt。”
