# Coworker 桌面端交互审计

审计日期：2026-07-20  
审计范围：Coworker 入口、首次加入、Composer、结果交付、工作记录，以及对应前端状态与布局实现。  
桌面基准视口：1280 × 720。

## 总体结论

“Pixel-Paper Diegetic Workspace”方向成立，人物、纸带、思考气泡和审批工作单已经形成了鲜明且一致的角色化体验，不需要退回传统聊天框。但当前实现把“完整结果”和“完整历史”都作为大面积常驻层，导致画布从唯一主舞台退居背景；同时 `composerOpen` 与 `activityLogOpen` 两个独立布尔值让多个主表面可以同时出现，交互完整性还没有收口。

当前状态适合作为设计原型，不建议直接以现有信息尺度进入正式版本。优先解决信息层级与表面状态模型，其价值高于继续增加动效或装饰。

## 现场证据

### Step 1：初始入口 — 健康

证据：`01-entry.png`

- 人物位于左上安全区，入口明确，没有挤压画布工具。
- 名称在人物下方，角色与操作对象的关系清楚。
- 风险：标签“和 Coworker 对话”仍把用户心智拉向聊天产品，建议改为更任务导向的“交给 Coworker”或“开始一起工作”。

### Step 2：首次点击与加入 — 基本健康

证据：`02-first-click-join.png`

- 加入授权说明清楚，明确“读取画布”和“修改前审批”。
- 500px 工作单尺度对首次授权是合理的，因为这是低频且高解释需求的状态。
- “工作记录”在首次授权前没有价值，应暂时隐藏，减少无效选择。

### Step 3：Composer — 基本健康，但入口语义不稳定

证据：`03-composer.png`

- 510px 宽度、两行输入和独立发送动作适合桌面画布。
- Enter、Shift + Enter 和 IME 处理完整。
- Coworker 作为真实协作者加入后，tldraw 的远端 cursor/chat 提示可能压住 Composer 辅助文案；需要为 Coworker cursor 设计固定避让或降低其提示层级。
- 当前人物点击承担“打开输入 / 收起输入 / 间接恢复旧结果”三重含义，表面上是 toggle，实际心智不稳定。

### Step 4：完整结果 — 有明显尺度风险

证据：`04-result-note.png`

- 实测结果便笺为 620 × 460px，占 1280 × 675px 画布可用面积约 33%；包含人物在内的舞台包围盒为 776 × 544px，占画布包围面积约 49%。
- 六点普通说明已经填满正文区，证明问题不是极端长文本才触发。
- 纸张视觉辨识度高，但标题、编号、宽左边距、1.9 行高和 1.25rem 段间距共同降低了信息密度。
- 普通文本答复不应默认使用“完整阅读态”；默认应先交付摘要，完整正文由用户显式展开。

### Step 5：结果与工作记录并列 — 不合格

证据：`06-result-with-log.png`

- 结果便笺和 420px 工作记录同时展开后，从 x=32 覆盖到 x=1246，几乎占满整个桌面宽度。
- 工作记录与 tldraw 右侧样式面板相互遮挡，并压到下方工具区。
- 同一份回复同时在结果便笺和工作记录中重复出现，形成内容重复和视觉竞争。
- 这是 P1 问题：工作记录、完整结果和 Composer 必须互斥，不能依赖用户自行收起。

### Step 6：结果后继续推进 — 可完成，但缺乏工作意图控制

证据：`07-composer-with-log.png`

- 点击人物会打开 Composer，并让旧结果消失；关闭 Composer 后旧结果再次出现。
- 用户无法明确表达是在补充约束、调整方向，还是要求 Coworker 继续推进当前工作。
- 当前工作记录只保存在 React 内存中，切换房间或刷新会清空，因此“上一次输出”并不是稳定能力。

## UI 与 UX 评审

### 信息尺度

不同阶段需要不同面积，不能统一追求“角色感的大道具”：

| 阶段 | 建议默认宽度 | 建议默认高度 | 判断 |
| --- | ---: | ---: | --- |
| Composer | 480–520px | 100–180px | 当前基本合理 |
| 思考气泡 | 240–320px | 60–100px | 当前合理 |
| 审批工作单 | 540–620px | 按真实计划展开 | 高风险决策，可保持较大 |
| 结果摘要 | 420–480px | 180–260px | 应成为默认交付态 |
| 完整结果 | 560–620px | 上限 440–480px | 只在用户显式展开后出现 |
| 工作记录 | 360–420px | 桌面右侧独占 | 与其他主表面互斥 |

结果摘要建议只展示任务化标题、2–4 行内容预览、完成回执和主动作。完整阅读态可以保留现有编辑部纸张风格，但正文行高建议降至 1.65–1.72，段间距降至 0.75–0.9rem，预览态不显示行号和大 folio。

### 点击 Coworker 的合理语义

人物入口应该保持一个稳定含义：**开始或继续输入任务**。它不应该同时作为历史结果的隐式开关。

推荐行为：

1. 点击人物始终打开并聚焦当前 room 的工作指令 Composer；再次点击只负责收起 Composer。
2. 新结果完成后自动出现“结果摘要”，而不是完整正文。
3. 打开 Composer 时，把上一份结果收成可见的小型“上次交付”条目，不要完全消失。
4. 使用“补充要求”“调整方向”“继续推进”等工作语言，不提供“新任务”或“继续追问”。创建新 room 才代表开始另一项任务。
5. “查看完整结果”和“工作记录”是两个独立的次级入口，且与 Composer/结果正文互斥。
6. 用户开始操作画布时，结果摘要自动缩成 Coworker 身旁的交付徽记，避免持续遮挡。

## 技术评审

### 做得好的部分

- 业务 phase 从 conversation/timeline 派生，没有复制第二份画布事实源。
- 纸带 `handoff` 是明确的短生命周期表现状态，与真实请求状态分离。
- approval identity、operation token、room epoch 和本地 pending 阻止了串房、竞态和重复审批。
- Composer 保留原生表单、IME、键盘和可访问性语义。

### 需要收敛的部分

1. `composerOpen` 和 `activityLogOpen` 是独立布尔值，可形成 Composer + history、result + history 等无意组合。应改为互斥的展示状态，例如：

   ```ts
   type CoworkerSurface =
     | { kind: "closed" }
     | { kind: "composer" }
     | { kind: "result-preview"; turnId: string }
     | { kind: "result-expanded"; turnId: string }
     | { kind: "history" };
   ```

   approval、thinking、executing 仍由业务 phase 强制覆盖，不写入这份 UI intent。

2. `showResultNote` 只排除了 `composerOpen`，没有排除 `activityLogOpen`，因此结果与历史可以并列。当前 CSS 也为两列同时展示预留了 1214px 宽度，进一步放大了问题。

3. 结果组件直接消费全部 `latestText`，只有“完整便笺”一种呈现。应先生成纯前端可验证的 preview model，例如标题、首段摘要、段落数量、是否有画布结果，再由同一文本源渲染 preview/expanded 两种视图。

4. `splitSemanticParagraphs` 通过正则去除 Markdown，但没有保留列表、标题、代码或表格的结构语义。中期应把流式文本解析成受控的 `ResultBlock[]`，避免纯文本越长布局越不可控。

5. 当前 `turns` 只在 React 内存中保存，切换 room 时显式清空。短期应把产品文案明确为“当前 room 的工作轨迹”；若要提供稳定的“上次交付”，应建立 room-scoped 后端记录与保留策略，不能塞进 tldraw document，也不建议无边界写入 localStorage。

## 桌面端范围收敛

按当前需求，建议声明最小桌面视口 1024px，并删除：

- `globals.css` 中 `max-width: 679px`、`max-width: 379px` 和仅为触控设备准备的分支；
- 纸带动效的三套 mobile keyframes 与移动端 reduced-motion 方向；
- 结果便笺的 679px 高度覆盖；
- 设计说明和 QA 中的移动端承诺。

预计可以移除约 250 行响应式 CSS 与三套动画分支。`prefers-reduced-motion`、桌面小窗口保护以及 200% 浏览器缩放韧性仍应保留；这些属于可访问性和桌面可靠性，不等于移动端支持。

## 优化路线

### P1：先修交互结构

- 删除移动端分支，明确桌面支持边界。
- 以 `CoworkerSurface` 互斥状态替换两个独立布尔值。
- 规定人物点击只负责 Composer；result/history 使用显式入口。
- 禁止 history 与 Composer、结果正文同时出现。

### P1：再收敛结果交付

- 新增 `result-preview` 与 `result-expanded` 两级。
- 普通回答默认摘要；画布编辑默认完成回执；异常默认恢复建议。
- 增加“补充要求”“调整方向”“继续推进”“展开/收起”“复制”；只有真实 record IDs 时展示“在画布中查看”。

### P2：处理历史与上下文

- 短期把记录明确为当前 room 的工作轨迹。
- 需要跨刷新历史时，再设计后端 room-scoped persistence、权限和保留策略。
- 根据产品需要决定同一 room 内的持续工作如何映射到底层 run/thread；这些实现概念不能泄漏为用户可见的会话心智。

### P3：最后做视觉精修

- 压缩完整结果正文节奏，减少装饰占位。
- 给结果生成任务化标题。
- 让工作记录回归同一纸张语言，但降低视觉权重。
- 处理 tldraw Coworker cursor 提示与 Composer 的遮挡关系。

## 证据限制

- 本次视觉审计使用 1280 × 720 桌面视口和真实本地 Coworker 流程。
- 已检查 DOM 语义与相关 React/CSS 实现，但没有声称完整 WCAG 合规；屏幕阅读器、200% 缩放和长时间流式性能仍需专项验证。
- 本次只做审计，没有修改生产代码。
